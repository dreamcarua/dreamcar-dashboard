### Назви секретів у GitHub ≠ назви в `.env`
**Symptom:** новий воркфлоу читає `secrets.TELEGRAM_BOT_TOKEN` — порожньо; власника просять поставити секрет, який уже є.
**Cause:** у GitHub Secrets цього репо Telegram-секрети називаються `TG_BOT_TOKEN` і `TG_CHAT_ID` (так їх читає `meta-stats-sync.yml`); `.env.example` легасі-дашборду називає ті самі речі `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`. Інші наявні секрети: `FB_ACCESS_TOKEN`, `IG_USER_ID`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `GH_TEAM_NOTIFY_TOKEN`. SMM-чат заданий літералом у `smm-content-watchdog.yml` (`SMM_CHAT_ID`).
**Do:** перед тим як просити новий секрет — `grep -h 'secrets\.' .github/workflows/*.yml | sort -u`: список того, що вже є. Нові воркфлоу вживають `TG_BOT_TOKEN` / `TG_CHAT_ID`.

### Один процес, два канали запуску (ETL MySQL → Supabase)
**Symptom:** ETL стартував 96 разів на добу замість 48; половина з 324 хв/міс CI йшла в нікуди.
**Cause:** `schedule:` у воркфлоу (0,30) і pg_cron job у Supabase через `etl-trigger` (15,45) запускали той самий процес. Кожен ран 21 с, білиться як повна хвилина.
**Do:** перед зміною частоти будь-якого ETL — знайти ВСІ канали: `schedule:` у `.github/workflows/`, pg_cron у Supabase, `workflow_dispatch`, вебхуки. Головний канал — pg_cron; `schedule:` лише резерв 3×/добу зі зсувом :05.
**Seen:** 24.08.2026 · commit 6ef8963

### GitHub cron ходить у 2–4 рази рідше за розклад
**Symptom:** воркфлоу з `cron: */15` реально запускається кілька разів на годину або рідше.
**Cause:** планувальник GitHub Actions придушує й пропускає запуски; вираз `cron:` — не фактична частота.
**Do:** навантаження рахувати з логу ранів (Actions → workflow → runs) або з Billing → Usage, а не з виразу `cron:`. Для критичних за часом процесів — pg_cron.

### Білінг округлює кожен job угору до хвилини
**Symptom:** воркфлоу з 10-секундними холостими ранами коштує стільки ж, скільки хвилинний; `fb-ads-sync` — 1257 хв/міс.
**Cause:** одиниця тарифікації — job-хвилина з округленням угору; вартість визначає кількість ранів, а не тривалість.
**Do:** оптимізувати кількість запусків (нічний throttle, обʼєднання), не швидкість коротких скриптів. Кожен воркфлоу — з `timeout-minutes` (без нього зависла job тримає один із 20 конкурентних слотів акаунта до 6 годин).

### `gh run list --limit N` віддає останні N ранів, а не всі за період
**Symptom:** оцінка навантаження Actions занижена у 20 разів (356 ранів замість 5854; 31 093 хв за серпень), на цій цифрі ухвалено рішення приватизувати репозиторії — квота вигоріла за 3 дні й зупинила прод.
**Cause:** ключ `--limit` обмежує вибірку, а не період; перед тим та сама метрика через wall-clock `startedAt→updatedAt` завищила на 31% (у різницю входить черга).
**Do:** будь-яка цифра про CI — з Billing → Usage. Форма звіту (розбивка по процесах, динаміка по днях) створює довіру, якої дані не заслуговують: перевіряти першоджерело саме там, де все залежить від однієї цифри.
**Seen:** 24.08.2026 · ✅ репо повернуто в public 27.08

### MV не фільтрує угоди по датах — подвійний рахунок між циклами
**Symptom:** проєкт показує вдвічі більше оплат і виручки, ніж було.
**Cause:** `mv_dashboard_projects_stats` джойнить угоди лише по збігу мітки з `dashboard_projects.deal_project_values`, без `date_start..date_end`. Одна мітка у двох проєктів = ті самі оплати в обох.
**Асиметрія, яка це підсилює:** у `mv_dashboard_projects_stats` угоди джойняться ЛИШЕ по мітці (`d.project = ANY(deal_project_values)`), а рекламний спенд і ручні витрати — ЛИШЕ по вікну `date_start..date_end`. Тобто проєкт може зібрати виручку за межами свого вікна, але ніколи не збере за ті самі дні витрати: ROAS і P&L спотворюються в обидва боки. Гірше, коли `date_start = date_end` (у червневого iPhone-проєкту вікно — один день 06.06): виручка за місяць, спенд за добу.
**Do:** нова мітка на кожен цикл (тригер колізій уже стоїть). Фікс класу помилки = фільтр по датах у MV, але він перерахує історичні цифри всіх проєктів — рішення власника.
**Справжня причина (знайдено 04.09.2026):** мітку ставить не ETL, а тригер `tg_deals_normalize_project` на `dashboard_deals` (BEFORE INSERT OR UPDATE). Він мапив префікс `deal_name` на назву проєкту БЕЗ дати: усе, що `DCI-iphone-%`, ставало `IPHONE 17 PRO MAX`. Липневий цикл продавався з двох префіксів (`DCI-promax-` — новий лендінг, `DCI-iphone-` — невимкнені старі лінки), тож 905 оплат осіли в червні. Наслідок для будь-кого, хто спробує це «полагодити» руками: **UPDATE рядків без правки тригера відкочується тим самим тригером**.
**Виправлено 04.09.2026:** тригер став date-aware (`DCI-iphone-` у вікні 02-05.07 → `IPHONE 17 PRO MAX 2`), 905 pay + 191 pending перемічено, MV перебудовано. Бекап: `public._backup_deals_iphone_relabel_20260904`. Міграція: `etl/migrations/20260904_iphone_cycle_relabel.sql`.
**Детектор:** `public.v_project_label_bleed` показує мітки, що перетікають у вікна інших проєктів (поріг 50 угод). Перевіряти після старту кожного циклу.

### Звіт, який не читається, забирав із собою всі інші
**Symptom:** один поганий файл у `reports/` — і воркфлоу `report-to-telegram` падає, а решта звітів того ж пушу не доходить. У логу лише помилка `jq`.
**Cause:** цикл відправки йшов під `set -euo pipefail` і кликав `jq` без перевірки. Перший файл, що не розпарсився, убивав увесь крок. 14.09.2026 так замовк приватний міст `memory-kit` на добу: агент згенерував base64 **руками** (модель писала його токен за токеном) і поклав у `.json` замість JSON. Ознака: латиниця й цифри декодуються бездоганно, кирилиця — місиво.
**Do:** звіт пишеться звичайним UTF-8 JSON і починається з `{`; кодує інструмент, не модель — вміст, що починається з `eyJ`, уже знищено і не лагодиться. Воркфлоу оновлено 14.09.2026: нечитабельний звіт пропускається з гучним повідомленням у сам канал, недоставлений лишається в `reports/` (дошле повторний `workflow_dispatch`), а червоний run сам пише про себе в чат.

### Новий розіграш без `code`/`deal_aliases` краде alias старого проєкту
**Symptom:** активний розіграш (#21 AUDI Q7 Prestige) у дашборді показував 5 571 лід, але 0 оплат, 0 покупців, 0 ₴ виручки. У БД при цьому 5 893 угоди й 4 789 оплат.
**Cause:** `launches` для #21 мав `code=NULL` і `deal_aliases=NULL`. Auto-merge у `loadProjects()` (docs/index.html) підставив `code = id.slice(0,8)` = `424f1dbc`, а список значень `project` для угод визначав substring-матчингом назви по вибірці `dashboard_deals.select('project').limit(5000)` — БЕЗ `order`, тобто довільні 5000 рядків зі 100k+. Нове значення `AUDI Q7 PRESTIGE` у вибірку не потрапляло, зате там було старе `Q7` (розіграш AUDI Q7, груд. 2025), і умова `c.includes(dp)` дала збіг: `'AUDI Q7 PRESTIGE'.includes('Q7')`. Запит ішов з `project=in.(Q7)` по вересневому вікну → нуль рядків.
**Do:** створюючи розіграш у `/projects/`, одразу заповнювати `launches.code` і `launches.deal_aliases` — це єдине джерело, яке не вгадує. Перевірка з браузера: пропатчити `window.fetch` і подивитись, який `project=in.(…)` реально йде у `/rest/v1/dashboard_deals`. Виправлено 15.09.2026: список `project` береться з `mv_dashboard_filter_options` (повний distinct), fallback-матчинг не чіпає значення, вже закріплені за іншим проєктом, а зворотний напрям вимагає ≥ 4 символів.
**Seen:** 15.09.2026 · аудит дашборду на запит Вадима

### «Останні N днів» давали N+1 день
**Symptom:** «Останні 7 днів» показували spend 116 601 ₴, тоді як сума за 7 київських діб — 105 119 ₴. Розбіжність 11 %, не відтворювалась у SQL.
**Cause:** `applyPreset()` рахував `from = today − N`, `to = today`, а межі inclusive-inclusive → 8 діб для `7d`, 31 для `30d`, 61 для `60d`.
**Do:** для inclusive-діапазону віднімати N−1. Перевіряти пресети не по назві, а порівнянням з SQL за той самий календарний період у `Europe/Kyiv`.

### `PROJECT_REF_MAP` ключами по НАЗВІ, а `filters.project` — це code
**Symptom:** success rate на дашборді — фікція: «Всього лідів» рахувалось по всіх проєктах, «Оплачено» — по одному.
**Cause:** `PROJECT_REF_MAP` мав ключі `'MOTORCYCLE'`, `'AUDI E-TRON'` (назви), а `filters.project` тримає `code` (`motorcycle_jun2026`, `audi_e_tron`). Умова не спрацьовувала ЖОДНОГО разу з моменту появи, тож `fetchLeadsCount()` завжди повертав лічильник без фільтра по проєкту. Додатково `ilike '%DCI-audi%'` ловив би ще й `DCI-audiq7`.
**Do:** ключі — `code`; префікс закінчувати роздільником (`DCI-audi-`), інакше він ловить довші slug-и. Якщо мапінгу немає — повертати `null`, а не число з іншим охопленням: інакше знаменник конверсії тихо бреше. NB: `dashboard_webhooks` тримає ~14 днів історії, тож для завершених проєктів лічильник лідів недоступний у принципі.

### Account-level fallback виконавця переписує реальну атрибуцію
**Symptom:** у розрізі виконавців витрати fortunatos і artem чергувались по днях: 03–07 і 09.09 — лише fortunatos, 08 і 10–15.09 — лише artem. Ті самі `ad_id`, той самий рекламний акаунт. Ліди при цьому щодня йшли від обох.
**Cause:** `etl/sync_fb_ads.py` → `transform_row()`: коли FB не віддав `url_tags` (збій `/ads`, пагінація, права), спрацьовував last-resort мапінг `ad_account_id → executor_utm_term` і ШТАМПУВАВ на весь акаунт одного виконавця плюс вигадані `utm_source='facebook'`, `utm_medium='cpc'`. В акаунті CLUB UAH (`1057590556523878`) працюють двоє, у таблиці `ads_account_to_executor` він закріплений лише за `artem`. Справжні мітки з `url_tags` — `utm_term=fortunatos, utm_source=meta, utm_medium=post`. Підміна `meta/post → facebook/cpc` ламала ще й фільтр типу трафіку.
**Do:** account-level мапінг застосовний, лише коли в акаунті РІВНО один виконавець; інакше — carry-forward останнього відомого значення по `ad_id` (оголошення виконавця не міняє). Ніколи не вигадувати `utm_source`/`utm_medium`. Детектор: `select ad_id, count(distinct utm_term) from dashboard_ads_data where date_start >= … group by 1 having count(distinct utm_term) > 1`. Виправлено 15.09.2026; бекап зіпсованих рядків — `_bak_ads_utm_20260915`.
